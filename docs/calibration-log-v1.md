### T1 · 区间判别参数的老窗口测量（2026-09-20）

**目的**：为 `detectRange` 的 `rangeMaxHeightAtr` / `rangeTolAtr` / `zigzagAtrMult` 及新增的语义判据（包含率、触碰次数）提供数据依据，取代此前无依据的临时值。

**数据**
- 来源：`data.binance.vision` 官方公开数据仓库，`futures/um/monthly/klines/<SYMBOL>/1h/<SYMBOL>-1h-2025-{09,10,11}.zip`
- 完整性：每个压缩包均与其同目录 `.CHECKSUM` 的 SHA256 比对通过（60/60）
- 规模：20 个币 × 2184 根 = 43,680 根；无缺口；合计下载约 1.95MB
- 为什么不走实时 API：执行当天 `fapi.binance.com` / `api.binance.com` 从本机直连均为连接超时（`UND_ERR_CONNECT_TIMEOUT`），公开数据仓库可达。数据列格式与 `/fapi/v1/klines` 一致，走同一个 `toBars()` 入口

**选币（无挑选）**：UM · USDT · 永续 · 上市早于 2025-08-01 的合约（当前列表中共 379 个），按 24h 成交额降序，等距抽取 20 个：

`ARBUSDT STRKUSDT SYNUSDT AEROUSDT ZKUSDT MUBARAKUSDT ENSUSDT DEXEUSDT SPKUSDT GRIFFAINUSDT PARTIUSDT CATIUSDT DOGSUSDT MERLUSDT SSVUSDT AXLUSDT CELRUSDT SAFEUSDT MAVUSDT RPLUSDT`

**方法**
- 测量时**不设高度上限**（`maxHeightAtr = Infinity`），避免只看得到切点以内的区间
- 评估点：每 6 根取一个（步长 6），从第 182 根起（168 回看 + 14 ATR 预热），每配置 6680 个 (币, 时点)

**结果**：见 `docs/feature-spec-v1.md`「区间判别参数」（由架构会话定值后写入）。

**已知局限**

### T2 · 区间参数冻结与测量脚本入库（2026-09-20）

| `rangeTolAtr` | 0.5 | tol=1.0 只多约 9 个百分点覆盖，但 1 ATR 的"同一水平"过松 |

**语义变更**：检测结果改为三态。`range`（has_range）/ `no_range`（数据充足但无相干边界，是真实状态，特征值 0，**不缺失**）/ `unavailable`（数据不足，唯一的缺失）。T1 的原始覆盖率 33.8% 来自把包含率当门槛；改为特征后 has_range 覆盖率 = **85.3%**（cap 25、触碰 ≥ 2）。

**T1 数字的一处说明**：先前回报的 `heightAtr`/触碰分布（p50 = 3.6 等）包含"无满足触碰数的簇时退回窗口极值、触碰=1"的点。冻结后的实现**没有**这个回退（单次触碰不是水平）。触碰 ≥ 2 的覆盖率表两者逐格一致；仅 has_range 点的 `heightAtr` 分布因此略有变化（p50 3.6 → 3.2，p90 12.0 → 8.3；包含率 p50 0.55 → 0.53）。

**T2 复现结果（新实现，mult=2 / tol=0.5，6680 点）**
- 状态占比：range 85.3% / no_range 14.7% / unavailable 0%
- no_range 原因：上沿无 ≥2 次触碰的簇 471、下沿无 ≥2 次触碰的簇 278、上沿簇不高于下沿簇 233
- has_range（cap 25）按月：9 月 0.874 / 10 月 0.825 / 11 月 0.866
- has_range 的 `heightAtr` p10/p25/p50/p75/p90 = 1.48 / 2.17 / 3.24 / 5.09 / 8.26；包含率 = 0.27 / 0.38 / 0.53 / 0.71 / 0.86；swing 数 = 15 / 16 / 18 / 21 / 22

### T3 · 三态语义裁定、预登记备选与 train/serve 一致性探针（2026-09-20）

**裁定（架构会话，写入 `docs/feature-spec-v1.md`）**：缺失与 0 的判据是 **"0 说出来的那句话，在这个状态下是不是真的"**（R6），不是"能不能算出来"。

| 情形 | f1 / f3 | f2 |
|---|---|---|
| 数据不足（bar < 168，或 ATR 无效/为 0） | 缺失 | 缺失 |
| 数据充足、确认摆动点 < 4 | **0**（`no_range`） | **缺失** |
| 数据充足、摆动点 ≥ 4 但无相干边界 | **0**（`no_range`） | 照算 |

f2 的 0 是"无明确趋势"，在强趋势里说的是反话，所以不对称。`f3 = 0` 是把观察到的状态编码在连续量表最"不像区间"的一端，不是填补缺失；代码注释已写明，禁止改成中位数填充。

**预登记的备选（防止将来钓参数）**：若 P3 中 `f1`/`f3` 的 ΔBSS 接近 0，第一个要检验的假设是"摆动尺度选错了"，预登记备选为 **`zigzagAtrMult = 1.5`、`rangeTolAtr = 0.5`**。该备选**只允许在验证折上试一次**，结果无论好坏都如实记录；**不允许扫描 mult × tol 网格去找最好的一格**。

**参数敏感性的记账**：主配置 (mult 2, tol 0.5) 处在斜坡而非平台上。has_range 覆盖率（cap 25、触碰 ≥ 2）：tol 0.3 / 0.5 / 1.0 下，mult=1.5 为 89.2 / 93.3 / 96.0%，mult=2 为 72.4 / 85.3 / 94.7%，mult=3 为 23.4 / 38.5 / 61.6%。参数已冻结不再调整；上线后真正的风险是**时间稳定性**（该窗口内按月 0.874 / 0.825 / 0.866）。

**train/serve 一致性探针**（特征侧，无标签）：ZigZag 是路径依赖的，而线上只有最近 360 根、训练可以喂多年历史。用 T1 的 20 币 × 2184 根，在每个评估点比较"全历史上的 `analyzeStructure`"与"仅最近 360 根上的结果"：

- 6100 个评估点：`rangeState` 一致 **100%**，窗口内确认摆动点数一致 **100%**
- 其中 5180 个 has_range 点：上沿、下沿、触碰数、包含率逐值一致 **100%**（1e-9）
- 额外历史长度 <200 / 200–600 / 600–1200 / ≥1200 根四档均为 100%

结论：在冻结参数（lookback 168、360 根窗口）下，ZigZag 在回看窗口开始之前已重新同步，训练与线上不会因窗口起点不同而分歧。此性质已固化为回归测试 `train/serve skew guard`（`scripts/test-structure.mjs`）。仅在 1h 上验证；4h（lookback 84）待 P5 单独验证。

**同日描述性快照观察（当前快照，仅供设计参考，未用于选参数）**：589 个永续合约中，**128 个（21.7%）的当前资金费率恰好等于 0.0001**（基准值），147 个在其 ±0.00002 内；结算周期分布为 4h × 434（73.7%）、8h × 131、1h × 4、无数据 × 20。这直接关系 `a3_funding_z`（见审计意见），待 P2 回填费率历史后再实测其历史分布。

### T6 · 币安连通性诊断（2026-09-20，非数据实验，记录以免重复误判）

- 现象：`fapi.binance.com` / `dapi.binance.com` / `api.binance.com` 从本机直连均超时；`data.binance.vision` 正常。
- 系统 DNS 对三个 API 主机每次返回不同的非币安地址（应答注入）；经 DoH 拿到的 CloudFront 真地址上 **TCP 能连（40–211ms），但以 `fapi/dapi.binance.com` 为 SNI 的 TLS 握手被 `ECONNRESET`**。架构会话另做的对照：**同一 IP 换 SNI 为 `data.binance.vision` 则握手成功**。结论：过滤发生在 SNI 层，**修 DNS 无效**。
- 教训：只测到 TCP 连通不能证明应用层可用；网络诊断先分层（DNS → TCP → TLS → HTTP）。
- 交付：`scripts/binance-net.mjs`（`preflight` 显式报告路径与失败层次，握手被重置时抛错且不提供绕过；`createGet` 保留域名只替换地址解析；不使用 `HTTPS_PROXY`）、`scripts/check-binance-net.mjs`、`scripts/test-binance-net.mjs`。
- **未采取**任何规避手段（换 SNI、域前置、ECH、代理）：那已不是修 DNS，而是绕过网络层过滤，须由用户决定。
- 影响：币安实时接口的采集/回填与 `FUNDING_SCALE_FLOOR` 的测量挂起；`data.binance.vision` 的长期使用仍待用户授权。

### T7 · 标签 k 的分布测量（2026-09-20）

**目的**：三重障碍标签的 `k`（障碍宽度，单位 ATR%）待测量；规则：三类里任何一类 < 15% 或 > 60% 则 `k` 要调。W1 是已消耗窗口，在其上只看标签分布、不训练任何模型，不影响测试折。

**方法**：`scripts/measure-label-distribution.mjs`；W1 的 20 币，每 6 根取一点。障碍 = 入场价 × (1 ± (k·ATR% + cost))，成本 = 2×0.05% + 点差 + 滑点。**点差用各币"当前快照"的点差代替整个窗口**（没有历史点差，已知近似）；**滑点尚无约定估计**，只作敏感性（0 与 0.05%），不是选择。同一根 bar 内两个障碍都被触及 ⇒ 判"down"（默认，架构裁定），并统计其占比。ATR 用 1h ATR14。

**4h 头（h=4，滑点 0.05%，n=7220）**

|---|---|---|---|---|---|

1. **单一的 k 不能同时服务两个头。** k = 1.0 对 4h 健康，对 24h 的 flat 只有 1.3%（障碍按 **1h** ATR 设，24 根 bar 的走势远超 1 个 1h ATR）。24h 的可接受区间约为 k ∈ [2, 3]；随机游走的 √ 标度给出 k_24 = 1.0 × √(24/4) ≈ 2.45，落在区间内。**未选定**，待架构裁定。

3. down 比 up 略多（4h k=1：33.1% vs 28.5%；24h k=2.5：36.5% vs 35.0%）。这是 W1（2025-09 至 11 月）这个单一 regime 的漂移，不能推广；同 bar 政策的贡献可忽略。

**已知局限**：点差为当前值的代用品；滑点无估计；20 币、单一 91 天窗口。

### T10 · FUNDING_SCALE_FLOOR 冻结、a3 启用与 403 之后的采集策略（2026-09-20）

**判据作废**（架构裁定，承认错误）：T9 里"±5 的 clip 率 ≤ 2%"是一个**凭空的数字**，且它把两个互不相关的机制压成了一个指标——下限（防止 IQR≈0 时除零，只对缺乏真实尺度的点起作用）与 ±5 clip（缩尾，防极值主导线性模型）。T9 的分解证明它**不可达**：即使在下限完全不起作用的最大 IQR 段（≥ 0.3），clip 率也仍有 2.08%——那是资金费率厚尾自身的水平；要压到 2% 以下只能把下限抬到中位数以上，那时一半以上的点 z 退化成绝对偏离，直接违反 R2。**作废。**

**改成语义判据**：下限正确 ⟺ 它只对缺乏真实尺度的点起作用，且这些点产出的 z 语义正确。T9 的数据已完成该验证：
- IQR ≥ 下限（56.84% 的点）⇒ 下限按定义无影响；
- IQR = 0 且当前费率等于该常数（IQR=0 点的 82.55%）⇒ z = 0，真值是"费率一直没动，现在也没动"；
- IQR = 0 且当前费率跳变（17.45%）⇒ z 很大、clip 到 ±5，真值是"一个费率从不波动的币，今天动了"，本来就该是极端值。
三种情形语义全对，**下限通过**。

**冻结**：`FUNDING_SCALE_FLOOR = 0.009252`（%/天，W1 非零 IQR 的 p10），clip 边界 ±5。**clip 率 5.82% 记为诊断量，不作门槛。** **`a3_funding_z` 启用**（代码 `lib/indicators/features/funding.ts`）。**预先登记**：若 P3 中 `a3` 的 ΔBSS 接近 0，备选假设是"±5 对厚尾饱和过度"，备选值 ±10，**只在验证折上试一次**，结果无论好坏都记录。

### T11 · regime 覆盖门槛（2026-09-20，设计已定，切点待数据）

**动机**：a3 在 W1 只在 −5 侧饱和（5.03%）而几乎不在 +5 侧（0.79%），不是分布平移，而是**饱和模式本身随 regime 变化**：牛市里费率抬升，饱和会跑到 +5 侧，被截断的是不同的尾巴。只在单一行情里验证过的模型输出自信的概率，是"假精度"的典型形态。`minTestSpanDays` 只是日历代理，看不见这件事；`minRegimes` 只在 handoff 草案里，代码里从来没有。

**设计**（架构裁定；代码 `lib/calibration/regime.ts` 与 `gate.ts`）
- **只用特征侧数据 g1（市场宽度）与 g2（BTC 波动分位），训练前冻结，不看标签**；模型看不到 regime 标签，所以不是选模型也不是标签泄漏。
- **两条边际要求，不做 g1 × g2 网格**：网格 9 个格子填不满，且 g1 与 g2 相关。分别要求测试折**同时含 g1 最高与最低三分位、g2 最高与最低三分位**，四个档位**各自** ≥ `minRegimeBinSamples` 个**有效**（唯一度加权）样本。两个轴都要，因为失效模式不同：g1 管方向性 regime（a3 的饱和侧），g2 管波动 regime（ATR 类特征）。
- **`minRegimeBinSamples = 100` 是判断值，非测量值**（注释已标）。
- **切点**：g1、g2 在**全部可用历史**上的三分位，**算一次，冻结为仓库里的常数，记入台账，每次运行不得重新推导**。这只是"高波动"这个词的定义；每轮重算会让门槛随数据漂移，那就什么也没门住。三分位边界是包含的（值 ≤ lower 为低档，值 ≥ upper 为高档）；非有限值不计入任何档。
- **fail-closed**：`regimeCutpoints` 默认 null，null ⇒ "regime coverage unverified: regime cutpoints not configured" ⇒ 不通过；报告没有覆盖、某个档位缺失/NaN/为 null/不足、只覆盖一个轴、覆盖是用**不同切点**算出来的、`minRegimeBinSamples` 未配置——一律失败，原因逐条列出。**没有"记录警告但放行"的口子。**
- 边界测试：null；四个档位分别为 0 / 99.9 / 恰好 100 / NaN / null；只覆盖 g1 的一档；某个轴整体缺失；某个轴很多、另一个轴很少；切点不一致、切点无效（lower ≥ upper、NaN、只有一个轴）；`minRegimeBinSamples` 为 NaN/null/undefined/0/字符串。

**后果（预期内，不是障碍）**：**在拿到跨 regime 的历史数据之前，P3 无法认证任何模型，面板不会显示概率。** W1 只有一个偏空 regime，无法用它来定切点，所以切点的测量本身要等多年历史。这给"需要多年历史"提供了具体理由：不是"样本更大"，而是"没有跨行情的数据就不能上线"。

**如实说明这个结果的含义（观察，不是决策）**：1h→4h 切换的 6 个事件里，4 次归档列在切换前最后一个旧行上仍写 1（该行结束的那个周期的长度），2 次已经写成 4（新周期）；4h→1h 与 8h→1h 的 9 个事件全部一致。也就是说这一列在 1h→4h 时的语义**并不统一**。规则 A 与归档一致的比例仍是 5511/5513（99.96%），不一致集中在"最后一个旧行"这一种场合。这与"第一个 4h 周期只有 3h"（API3USDT）出自同一现象：1h→4h 切换点附近的周期长度在币安自己的记录里就有多种写法。**是否影响 a3、影响多大、怎么处置，交架构会话裁定**；本读取不据此改任何东西。

### T16 · 周期 oracle 的独立复现，以及决策记录之后的事后观察（2026-09-21）

**独立复现（批次 1：51 个币 × 2025-08…11；明确标注为复现，不参与、也不能改变 T15 的决策）**：可比对 30,897 行，**全部一致，0 不一致**；语义事件只有 1 个（`TNSRUSDT 2025-11-19 17:00` 4h→1h，(4,1)，period_ending_at_row）；被拒绝行 0 个；复现的读取结论是 untested（事件 < 3）。它证明推断在稳态行上是对的，但对 1h→4h 那两个例外**没有任何信息**（批次 1 的 51 个币几乎没有周期切换）。

**以下全部是 T15 决策记录之后的事后观察（post-hoc）——只描述，不据此改任何东西，也不构成判读。**

1. **1h→4h 切换有三种对齐**（T15 的 6 个 1h→4h 事件加 API3）：(a) 切换落在间隔 4h 的行上（MYX 08-11、MYX 10-12、RED 09-27、SUPER 11-06）：最后一个旧行写 1h，第一个新行写 4h；(b) 新周期的第一次结算恰好落在整点，只隔 1h 就被写成 4h（FUSDT 11-06 04:00、MYX 09-20 12:00，也就是 T15 里的两个 lead 事件）；(c) 只隔 3h 就被写成 4h（API3USDT 09-21 08:00，规则 A 拒绝的那一行）。三种都符合"**归档列 = 该次结算时生效的名义周期**"，而不一定是"实际经过的时间"。
2. **费率是按名义周期报价的**：基准费率是每 8 小时 0.01%（0.00125 %/h）。在 oracle 文件里，三种周期列（1h n=4469、4h n=852、8h n=113）的"每名义小时费率"**众数都是同一个 0.00125 %/h**。切换行 FUSDT 04:00、MYX 09-20 12:00、API3 09-21 08:00 的费率是 **0.0050%**（4h 基准），尽管它们与上一行只隔 1h/1h/3h。所以 `daily = 费率 × 24 / 名义周期` 才对；**按实际经过时间归一化（规则 A 对 1h 间隔行；规则 B 对所有行）会在这类切换行上把 daily 高估 4 倍**（3h 间隔行高估 4/3，规则 A 因拒绝它而不受影响，规则 B 反而会带进来）。
3. **影响面很小，但会随数据量增长**：本地 359 币、221,655 行里，紧邻周期切换（前一间隔 ≠ 后一间隔）的行只有 **31 个（0.014%）**，涉及 22 个币，被规则 A 拒绝的 1 个。当前对 a3 的影响可以忽略；P3 拉多年历史时切换次数会高一个量级（8/9/10/11 月 = 3/5/6/16 次且在加速），届时不能忽略。
4. **规则 A 与 B 都不是对的**：两者都用"实际间隔"，而费率按"名义周期"报价；差别只在切换行上。真正的问题不是 A 与 B 之争，而是**推断无法在切换边界上恢复名义周期**——名义周期既不总等于前一间隔（(b)），也不总等于后一间隔（(a) 的最后一个旧行）。
5. **一个候选规则 C（事后提出，必须在新数据上预登记并验证，不得因本次观察直接采用）**：丢弃"前一间隔与后一间隔吸附后不相等"的行（紧邻周期切换的行），以及被拒绝的行。在已读的 12 个文件上，(a)(b)(c) 三类的可疑行都会被它挡掉，代价是每次切换丢 1–2 行（0.014%）；但"在事后看过的 12 个文件上表现好"不构成验证，需要**新的、未读过的**切换事件（其它月份/币），这需要用户批准的额外下载。

**遵守的纪律**：T15 决策（escalate）已先于复现与本节写入；本节的观察在决策之后产生，任何规则变更都必须先预登记、再在新数据上验证。规则 A 仍是生产规则，未改动。

### T17 · 周期切换边界行的丢弃规则落地（2026-09-21）

**裁定（架构会话；T15 的 escalate 判决原样保留，不做事后重新解释）**：费率按**名义周期**报价（每名义小时费率在 1h/4h/8h 上都是 0.00125 %/h），所以 `daily = 费率 × 24 / 名义周期`；**规则 A 与规则 B 都用实际间隔，两者都错**——预登记问的"A 还是 B"是一个错误的问题，正确答案是"都不是"。这次预登记被严格执行、得出了诚实的 escalate，**真正的答案来自记录之后的事后观察**；先按预登记如实结案、再让事后观察以事后观察的身份入账，两份证据才都可信。预登记防的是"自欺"，防不了"问错问题"，两样都要有。

**为什么不需要新数据验证，而 T16 里我建议要**：规则 C 不是"更好的估计"（性能主张，须在未读过的数据上验证），而是"此处名义周期不可知，所以不估、按缺失处理"（拒绝主张）——正是 R4/R6 的既有原则用在一个新发现的场合。代价有界（每次切换丢 1–2 行 / 约 180 行窗口）；误判方向安全（漏结算同样触发，同样是不可信的行）；判据是逻辑刻画而不是拟合阈值（"前一间隔 ≠ 后一间隔"就是"该行位于边界"的定义）。**无论真相如何都不会更糟的改动，不需要证明它更好。**唯一确实要验证的是**漏检率**（没被捕获的边界行），留作 P3 预登记，届时多年历史里切换事件多一个量级，不需要额外下载。

**实现**（`lib/indicators/features/funding.ts` 的 `normaliseFunding`，生产路径）：一行被丢弃，当且仅当 (1) 它与上一行的间隔不在 {1,2,4,8}h ±10% 内，或 (2) 它与下一行的间隔吸附后 ≠ 它与上一行的间隔（位于周期切换处）。首行无前驱、被丢弃。测试：稳态只丢首行；FUSDT 形态（1h 结算后第一次落在 4h 基准上，费率 0.0050%）的行被丢弃，按实际间隔会得到 0.12%/天而名义周期给出 0.03%/天；一次周期切换只多丢 1 行；第一个正常的 4h 行保留；`checkIntervalInference`、规则 B/被拒绝行判读的既有测试按新行为更新。

**一个必须如实写下的因果性局限（R1，禁止前视）**：判据需要**后一行**，而决策时刻最新一行没有后继。所以规则能修正窗口内部的行（中位数/IQR 以及之后的"当前值"），**修不了"最新一行恰好就是尚未被识别的切换行"的那几个小时**——它被原样使用，直到下一次结算揭示它。这是无法用因果信息弥补的：那一行与普通的 1h 行在当时不可区分。已用测试固定：最新行保留、后继出现后才被丢弃；任意 i 处 a3 与"数组里是否存在之后的行"无关（前缀不变性）。
- **丢弃率**（359 币，W1+前导，221,655 个被判定的行）：**32 行（0.014%）**，22 个币；与预期的 0.014% 一致，判据没有问题。
- **暴露时长**（规则覆盖不了的部分）：W1 内 784,056 个小时级决策点里，有 **34 个（0.0043%）**落在"最新一行之后被证明是边界行"上。这是**上界**：边界行只有在"实际间隔 ≠ 名义周期"时才真的算错（(b)(c) 类），而"最后一个旧行 (a)"其实是对的，两者在当时不可区分。外推到线上约 526 币 × 8760 小时：按 W1 平均切换率约每天 0.5 个币-小时；11 月的切换率约为 W1 平均的 2.7 倍，按那个速率上界约每天 1.5 个——与架构估计的"每天约 1–2 次"在 11 月速率下相容。真正算错（4 倍偏差）的只是其中 (b)(c) 类，约占边界行的 1/3 以下，且只持续到下一次结算。
